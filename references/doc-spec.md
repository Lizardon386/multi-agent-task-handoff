# 多agent间工作任务交接手顺 · 规则全文（完整版）

适用于任何"一个根目录下按任务建子目录"的 agent 工作区（本机为 `D:\agent_workspace`）。

## 两份文档，职责不许混

| 文件 | 读者 | 回答的问题 | 变化频率 |
|---|---|---|---|
| `README.md` | **用户 / 使用者** | 这是什么、**为什么这么设计**、怎么用 | 稳定，只在设计或用法变化时改 |
| `CONTEXT.md` | **agent / 协作者** | 做到哪一步了、下一步做什么、有什么坑 | **每次会话都要改** |

## 命名

### 固定名（不许变体、不许翻译）

`README.md`、`CONTEXT.md`、`AGENTS.md` 这三个名字是规范本身的一部分：全大写、不带中文别名、不改拼写。

### 禁的是"角色重复"，不是"多一个文件"

旧版这条写成"只有两个名字，禁止 `使用说明.md` / `部署说明.md` / `进度.md`"，容易被误读成"任务目录里不许有第三个文档"。准确的边界是按**角色**判：

- 一个文件的职责是「给人看的说明」→ 它就是 `README.md` 的复制品，禁止另立，内容并回 README。
- 职责是「给 agent 看的交接/进度」→ 它是 `CONTEXT.md` 的复制品，禁止另立，内容并回 CONTEXT。
- 职责是**任务本身的产出**（设计稿、评审意见书、决策件、评估报告、问题清单）→ 允许独立存在，见下条。

判断口诀：问"这份东西是给谁看的说明，还是我干的活本身？"前者并回双档，后者独立成文。

### 其他输出文档必须中文命名

交付物文档的文件名一律用中文。理由很实际：读者是中文同事，文件会被转发进群聊和飞书，英文名对方得先猜是哪个、还得下载才看得懂，而中文名在文件列表里就能完成沟通。

正例：`设计总览.md`、`架构全文.md`、`归属决策件.md`、`他人设计稿评审意见书.md`、`会前问题清单.md`。
反例：`design-overview.md`、`architecture-full.md`、`notes.md`。

**豁免（不要求中文名）：**

| 情形 | 为什么豁免 |
|---|---|
| `README.md` / `CONTEXT.md` / `AGENTS.md` | 规范固定名 |
| 非 `.md` 交付物（`.docx` / `.pdf` / `.png`） | 要发回供应商或对方系统，必须与原件同名，改了版本对不上 |
| `_` 前缀的机器产物（如 `_ref-*.txt`） | 提取/转储的中间件，不是给人读的文档 |
| `archive/`、`inputs/` 等子目录内的文件 | 历史留档与外部原件，改名要追溯全部引用且没有收益 |
| 脚本、代码、配置 | 跟随各自语言与工具的命名惯例 |

`check-docs.sh` 的 `[名]` 只扫**任务目录顶层的 `.md`**——只看顶层就自动放过了 `archive/` 与 `inputs/` 子目录，非 `.md` 与 `_` 前缀在代码里显式豁免。文件名纯 ASCII（不含任何非 ASCII 字节）即判失败。

## README.md 章节（顺序固定）

```
# <任务目录名> · 设计思路与使用说明
> 面向使用者：……。任务进度与 agent 交接记录见同目录 CONTEXT.md。
> 最近更新：YYYY-MM-DD
## 一句话说明
## 设计思路            ← 必须有「决策 / 理由 / 代价」三列表，写清取舍而不只是结论
## 快速开始            ← 最短能跑通的命令序列
## 使用说明            ← 完整流程、可覆盖参数、日常操作表
## 产物与目录          ← 文件清单（哪些是交付物、哪些是本机工具、哪些要传入内网）
## 限制与注意事项      ← 用户视角的边界与误操作风险
```

## CONTEXT.md 章节（顺序固定）

```
# <任务目录名> · 会话上下文与进展
> 本文件是任务交接档案，供 agent 实时跟进。改动产物后请更新「当前状态」「变更记录」。
> 最近更新：YYYY-MM-DD（<来源>）
## 背景与目标
## 当前状态
## 计划 / 待办        ← 用 - [ ] 复选框，已完成打勾不删
## 关键约束与注意事项  ← 不可逆操作、就地修改风险、幂等性、外部硬约束
## 变更记录            ← - YYYY-MM-DD <来源agent>：<摘要>
## 给下一个 agent 的追加区
```

额外小节允许（如 `日常运维`、`性能与磁盘预期`），既定六节**不许删**。

## 分工红线

- 进度、验证记录、待办、遗留问题**只写在 `CONTEXT.md`**。README 里不写"我们测了什么、还剩什么"。
- 设计取舍与操作步骤**只写在 `README.md`**。CONTEXT 里不复制手册，只写"入口文档是 README.md"。
- 两边都需要的关键事实（端口、路径、硬性磁盘要求）：CONTEXT 里一行引用，不重述细节，否则必然失同步。
- 代码/脚本能自解释的不抄进文档。文档写**为什么**和**坑**，不罗列**是什么**。
- `设计思路` 三列表是硬要求：每个决策都要写代价。只有结论没有代价的表等于没写。

## 产物链接（强制）

任何向用户呈现的文件产物，一律写成**可点击的 Markdown 绝对路径链接**，不接受裸文件名、反引号路径或纯文本 `D:\...`——那些在侧边栏点不开，用户得自己去翻目录。

```markdown
[game.js](file:///D:/agent_workspace/uno-webgame/game.js)
```

- 协议固定 `file:///`（三斜杠），路径一律正斜杠；Windows 的 `D:\x\y.js` 要写成 `file:///D:/x/y.js`。
- 指向具体行时，行号写在**链接文字**里而不是 `#L42` 锚点：`[game.js:42](file:///D:/agent_workspace/uno-webgame/game.js)`。锚点形式未经验证，不依赖。
- 适用面：聊天回复里的产物清单、`README.md` 的「产物与目录」、`CONTEXT.md` 的「当前状态」与「变更记录」。
- 反例（都点不开）：`` `game.js` ``、`D:\agent_workspace\...\game.js` 裸写、相对路径 `./game.js`。
- `check-docs.sh` 对「产物与目录」里没有任何 `file:///` 链接的 README 报 `[链]` 并**判失败**（2026-10-10 起由告警升级：告警在实践中被 `tail` 截掉过，等于没有）。

## 会话节奏（每个 agent 都执行）

1. **进目录先读**：`CONTEXT.md` → `README.md`，再动文件。
2. **开新任务即建档**：`bash tools/init-task.sh <任务名>` 铺骨架，不许"会话结束再补"。空骨架会被自检判不合规。
3. **收工必更新**：改了产物 → 更新 README 对应章节；有了新结论/改动/踩坑 → 更新 CONTEXT 相应小节并在「变更记录」留一行。
4. **两侧同步日期**：两档顶部「最近更新」必须与实际改动同日，且两档彼此一致。
5. **自查闸门**：`bash tools/check-docs.sh` 退出码 0 才算本次会话收尾完成。
   - 检查项前缀：`[缺]` 文件不存在、`[构]` 缺章节、`[占]` 模板占位符、`[空]` 骨架未填、`[链]` 产物清单缺 `file:///` 链接、`[名]` 顶层输出 `.md` 未用中文命名、`[期]` 两档「最近更新」日期不一致、`[新]` 缺「最近更新」、`[旧]` 超期。
   - 只有 `[旧]` 是告警（用 `STALE_DAYS` 调天数）——已完结任务本就该停在最后改动那天，硬失败会让人绕过检查。`[链]` 与 `[期]` 是失败项：它们描述的正是"文档没跟着改动走"，放任就等于放弃这条规矩的执行下限。
   - **顶部日期必须写在 `> 最近更新：YYYY-MM-DD` 这一行**（紧跟 H1 的 blockquote）。`[新]`/`[旧]`/`[期]` 只认这个锚定形式；正文里再出现「最近更新：某日期」不会被当成顶部日期。早先版本没锚定，实测出现过"顶部漏日期、正文有日期"的文档被 `head -1` 拿正文那行去判 `[旧]` 然后整个闸门判 OK 放过——这类静默漏检比报错更危险。
   - 跑闸门**不要用管道截断输出**（`| tail -2` 会把违规行吃掉，只剩结尾那句 OK，制造假绿灯）。

## 边界与特例

- `tools/`、`templates/`、`node_modules/`、`.git/` 是基础设施与素材，**不参与自检**（工具目录自身照样写了双档当范例）。
- 一次性/纯搬运目录也要双档：README 可以短，但「设计思路」取舍表必须写清为什么这么做，CONTEXT 的「变更记录」必须有最后一行状态。
- 引入外部 git 仓库源码的任务，双档照样要写，源码自身规范另计。
- 跨任务共用信息：写在本目录 CONTEXT.md 的「关键约束」里并引用另一任务的文档名，不要复制粘贴。

## 为什么要有这条规矩

会话上下文是易失的：换会话、换 agent、换机器后，新人只能从目录列表猜意图，猜错就要返工。
`README.md` 存"为什么这么设计"（避免反复重议），`CONTEXT.md` 存"到哪了"（避免重复劳动和踩已知坑）。
规则必须有可执行的下限（`check-docs.sh`），否则只会在第一次执行后被稀释。
